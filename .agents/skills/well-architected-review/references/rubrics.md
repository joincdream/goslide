# Well-Architected 정성 평가 세부 채점 루브릭 (Scoring Rubrics)

본 문서는 Goslide 코드베이스의 정성적 아키텍처 품질을 1~5점 척도로 객관적이고 일관되게 채점하기 위한 세부 기준표입니다.
각 메트릭은 5점 만점이며, 20%의 가중치를 곱해 20점 만점으로 환산됩니다. (총 100점 만점)

---

## M1. 단방향 파이프라인 & 관심사 분리 (SoC / Coupling) [가중치: 20%]

단방향 데이터 흐름(`Source` ➔ `Parser` ➔ `Model` ➔ `Renderer` / `Exporter`)과 패키지 간 관심사 분리를 평가합니다.

| 점수 | 평가 기준 (Criteria) |
| :---: | :--- |
| **5점 (최우수)** | • 패키지 역참조/순환의존성이 0건임.<br>• 각 패키지가 자신의 단일 책임만 수행하며, 하위/상위 계층의 내부 구현을 전혀 모름.<br>• `theme`, `parser`, `model`이 상호 독립적이며 인터페이스로만 소통함. |
| **4점 (우수)** | • 순환 의존성은 없으나, 패키지 간에 사소한 결합도(예: 불필요한 모델 필드 노출 등)가 1~2군데 관찰됨. |
| **3점 (보통)** | • 동작은 하나, 특정 계층이 다른 계층의 세부 구현에 과도하게 의존하여 변경 시 파급 효과가 발생함. |
| **2점 (미흡)** | • 계층을 우회하거나 파이프라인 단계를 건너뛰는 코드가 존재함. 강결합 발생. |
| **1점 (실패)** | • 순환 참조(Circular Dependency)가 발생하거나 역방향 의존성으로 패키지 분리가 무의미함. |

- **하드 체크포인트**: `go list -f '{{.ImportPath}} -> {{.Imports}}' ./...` 실행 시 역참조 0건 필수.

## M2. 단순성 및 YAGNI 원칙 준수 (KISS / ADR-001) [가중치: 20%]

오버엔지니어링(조기 과분할, 가상의 문제를 해결하기 위한 불필요한 연산기/레이어)을 배제하고 단순성을 유지하는지 평가합니다.

| 점수 | 평가 기준 (Criteria) |
| :---: | :--- |
| **5점 (최우수)** | • [ADR-001](file:///home/yundream/myjob/cloit/Goslide/docs/okf/decisions-simplification.md) 폐기 결정(cascader, path, element 등)이 100% 반영됨.<br>• 브라우저 표준에 역할을 위임하고, 코드는 최소한의 핵심 로직만 간결하게 유지함.<br>• 프로덕션 파일 수가 20개 이내로 고응집을 유지하며, 데드코드가 0건임. |
| **4점 (우수)** | • 전반적으로 간결하나, 향후 확장을 위해 미리 만들어둔 빈 파일이나 주석 처리된 코드가 소수 잔존함. |
| **3점 (보통)** | • 불필요한 헬퍼나 유틸리티 함수가 여러 개 존재하며, 표준 라이브러리로 대체 가능한 로직을 직접 구현함. |
| **2점 (미흡)** | • 사용되지 않는 추상화 계층이나 복잡한 알고리즘이 포함되어 인지 부하를 높임. |
| **1점 (실패)** | • 요구되지 않은 복잡한 서브시스템(외부 브로커, 복잡한 캐싱 등)이 도입되어 유지보수가 극히 어려움. |

- **하드 체크포인트**: `golangci-lint`에서 미사용 코드(deadcode/unused) 0건 필수.

## M3. Go 관용구 및 인터페이스 적정성 (Idiomatic Go / ISP / DIP) [가중치: 20%]

Go 언어 철학(Small Interface, Composition, Explicit Error)과 객체지향 설계 원칙을 준수하는지 평가합니다.

| 점수 | 평가 기준 (Criteria) |
| :---: | :--- |
| **5점 (최우수)** | • 인터페이스가 1~2개 메서드로 극도로 간결하게 정의됨 (Single-method interface).<br>• 전역 가변 상태(Global mutable state)가 0건이며, `New...` 생성자를 통한 의존성 주입(DI) 준수.<br>• 블로킹/무거운 작업에 `context.Context`가 1번째 인자로 전달되고 취소 신호가 처리됨. |
| **4점 (우수)** | • 전반적으로 관용적이나, CLI 플래그 등에서 패키지 레벨 변수가 소수 선언되어 있거나 사소한 관용구 아쉬움이 있음. |
| **3점 (보통)** | • 인터페이스 메서드가 4개 이상으로 다소 비대하거나, 전역 캐시/상태가 부분적으로 사용됨. |
| **2점 (미흡)** | • 자바 스타일의 복잡한 팩토리/싱글톤 안티패턴이 적용되어 있거나 `context`를 무시함. |
| **1점 (실패)** | • 전역 가변 변수로 인해 동시성 환경에서 데이터 레이스 위험이 상존하고 인터페이스 격리가 부재함. |

- **하드 체크포인트**: 비즈니스 패키지 내 전역 가변 변수(Global state) 0건 필수.

## M4. 에러 맥락 및 실행 가능성 (Actionable Errors) [가중치: 20%]

오류 발생 시 사용자와 운영자가 원인을 즉시 파악하고 조치할 수 있는 구체적 맥락이 제공되는지 평가합니다.

| 점수 | 평가 기준 (Criteria) |
| :---: | :--- |
| **5점 (최우수)** | • Go 1.13+ 에러 래핑(`%w`)을 100% 준수하여 원인 추적 가능.<br>• 도메인 센티넬 에러(`ErrThemeNotFound` 등)가 정의되어 `errors.Is` 분기가 가능함.<br>• 에러 메시지에 실패한 파일 경로(`%q`), 테마명, 수치 등 **Actionable Context**가 명확히 포함됨. |
| **4점 (우수)** | • 에러 래핑과 센티넬 에러는 잘 되어 있으나, 일부 메시지에서 구체적인 식별자(경로 등)가 누락된 곳이 1~2군데 있음. |
| **3점 (보통)** | • `panic`은 없으나, 단순 문자열 에러(`errors.New`)가 래핑 없이 반환되어 호출 측에서 에러 타입 분기가 어려움. |
| **2점 (미흡)** | • 에러를 무시(`_ = doSomething()`)하거나 상위 계층으로 메시지 유실이 발생함. |
| **1점 (실패)** | • 라이브러리/코어 로직에서 `panic()`을 남발하거나 시스템 크래시를 유발함. |

- **하드 체크포인트**: 코어 로직 내 `panic()` 0건 필수.

## M5. 도메인 모델 불변성 및 확장성 (Immutability & Extensibility) [가중치: 20%]

슬라이드 IR(Intermediate Representation) 모델이 사이드 이펙트 없이 안전하며, 새로운 포맷(PDF/PPTX) 확장에 유연한지 평가합니다.

| 점수 | 평가 기준 (Criteria) |
| :---: | :--- |
| **5점 (최우수)** | • 파싱 완료된 `Deck`, `Slide` 모델이 외부 AST 라이브러리에 오염되지 않은 순수 도메인 모델로 유지됨.<br>• 렌더러와 익스포터가 모델을 읽기 전용으로 안전하게 소비하며, 데이터 레이스 가능성이 없음.<br>• 차기 마일스톤(HTML, PDF, PPTX)에서 기존 코드를 수정하지 않고 확장 가능한 OCP 구조를 가짐. |
| **4점 (우수)** | • 모델이 순수하고 안전하나, 일부 필드의 타입(예: 슬라이스 내부 가변성)에 대한 불변 캡슐화가 약간 아쉬움. |
| **3점 (보통)** | • 렌더러가 파싱 모델을 일부 직접 수정하거나, 특정 출력 포맷(HTML) 전용 필드가 모델에 혼재되어 있음. |
| **2점 (미흡)** | • 새로운 포맷을 추가하려면 기존 파서나 모델 구조체를 대폭 뜯어고쳐야 하는 구조. |
| **1점 (실패)** | • 파싱 모델과 렌더링 상태가 뒤섞여 동시 렌더링 시 심각한 상태 오염이 발생함. |

- **하드 체크포인트**: `model` 패키지가 외부 파서 AST 라이브러리(`goldmark/ast`)를 임포트하지 않을 것.
